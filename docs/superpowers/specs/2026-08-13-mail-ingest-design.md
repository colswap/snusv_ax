# 메일 수집(mail_ingest) 설계

- 작성일: 2026-08-13
- 상태: 설계 확정 대기
- 대상 자동화: `automations/mail_ingest` (신규), `automations/mail_reminder` (신규)
- 선행 스펙: [회계 송금 리마인더](2026-08-13-finance-reminder-design.md)

## 1. 배경

공용 메일 계정으로 하루 20통 이상이 들어온다. 스팸이나 뉴스레터는 거의 없고, 발송 실패 자동 반송만 예외적으로 섞인다. 즉 **대부분이 사람이 봐야 할 진짜 메일**이다.

현재 Slack 기본 Email 앱으로 채널에 포워딩하고 있으나, 그 앱은 메일을 **첨부 객체로 렌더링**한다. 채널에는 박스만 뜨고 내용이 보이지 않아 결국 메일함을 따로 열어야 한다. 설정으로 바꿀 수 있는 문제가 아니라 그 앱의 설계다.

더 근본적인 문제는 2025년에 조직 내부에서 이미 진단된 바 있다.

> 공유 계정의 경우, 누군가 읽으면 읽음 표시 되어서 답장 놓치기 쉬움

**읽음과 처리 완료가 구분되지 않는다.** 누가 열어보기만 해도 읽음이 되고, 그 뒤로는 아무도 그 메일이 미처리라는 걸 모른다.

## 2. 목적

1. 메일 내용을 슬랙에서 **바로 읽을 수 있게** 한다
2. ✅ 리액션으로 **읽음과 처리 완료를 분리**한다
3. 24시간이 지나도 아무도 확인하지 않은 메일을 채널에 다시 띄운다

## 3. 범위

### 포함
- Gmail 수신 메일을 `#inbox` 채널에 본문과 함께 게시 (`mail_ingest`)
- 24시간 경과 후 ✅ 없는 게시글을 같은 채널에 요약 게시 (`mail_reminder`)
- 위를 위한 `shared/` 리팩터링 (§6)

### 제외
- 답장 여부 자동 판정. 처리 완료 신호는 답장이 아니라 ✅ 리액션이다
- 슬랙에서 메일 답장 보내기 (양방향)
- 담당자 지정. 리마인드는 개인 DM이 아니라 채널에 게시한다
- 첨부파일 슬랙 업로드. 파일명만 표시하고 원문 링크로 넘긴다

## 4. 동작 명세

### 4.1 수집 (`mail_ingest`)

10분마다 실행한다. 하루 20통이면 실행당 0~2통이다.

대상 메일:
- 받은편지함에 있고
- `slack-posted` 라벨이 **없고** (중복 방지)
- 자동 반송이 아닌 것 (Gmail 검색어로 제외)

각 메일을 `#inbox`에 게시한 뒤 **`slack-posted` 라벨을 붙인다.** 이 라벨이 "어디까지 가져왔는가"를 대신하므로 별도 상태 저장소가 필요 없다.

### 4.2 게시 포맷

```
📨  *창업지원단 동문기업 홍보 요청*
발신  홍길동 <hong@snu.ac.kr>
수신  2026-08-13 14:22

안녕하세요, 서울대 창업지원단입니다.
(본문 전문)

📎 첨부: 신청서.hwp, 안내문.pdf
🔗 <Gmail에서 열기>

✅ 확인했으면 체크
```

본문은 자르지 않는 것이 기본이다. 다만 Slack 텍스트 블록은 3,000자 제한이 있으므로, 초과하는 긴 공문만 잘라내고 "…전체는 원문에서"를 덧붙인다.

HTML 메일은 Gmail의 평문 본문을 쓴다. 인용된 이전 대화(`>` 블록)는 잘라낸다 — 스레드가 길어지면 인용문이 본문보다 길어진다.

### 4.3 리마인드 (`mail_reminder`)

매일 1회, `#inbox`에서 아래를 만족하는 게시글을 찾는다.

- 이 봇이 올린 메일 게시글
- 24시간 이상 경과
- ✅ 리액션 없음
- ❌ 리액션 없음

1건 이상이면 **같은 채널에** 요약을 게시한다. DM이 아니다.

```
📮 아직 아무도 확인 안 한 메일 4건입니다.

1. 창업지원단 동문기업 홍보 요청 — 3일 경과 · <원문 보기>
2. …

확인하셨으면 해당 메시지에 ✅ 를 달아주세요.
```

**DM이 아니라 채널인 이유**: 메일에는 담당자가 정해져 있지 않다. 개인에게 보내려면 먼저 담당을 지정해야 하는데, 그러면 "아무도 안 맡은 메일은 영원히 조용해지는" 구멍이 생긴다. 채널에 띄우면 누구든 집어갈 수 있고 구멍이 없다.

## 5. 실행 환경

### 5.1 수집은 Google Apps Script

| 방식 | 비용 | 버전 관리 | 상태 저장 | 비밀 관리 |
|---|---|---|---|---|
| **Google Apps Script** | 무료 | `clasp`으로 git | 불필요 (Gmail 라벨) | 불필요 |
| Python + IMAP on Actions | 무료 | 이 레포 그대로 | 필요 | 앱 비밀번호 |
| Make.com | 무료 1,000 ops/월 | 레포 밖 | 불필요 | 플랫폼 관리 |
| Zapier | 무료 100 tasks/월 | 레포 밖 | 불필요 | 플랫폼 관리 |

Zapier는 무료 플랜이 트리거 1 + 액션 1의 2스텝 제한이라 "수신 → 포맷 → 게시"가 성립하지 않는다.

**Google Apps Script를 택한다.**

- 구글 계정 권한으로 실행되므로 OAuth 리프레시 토큰이나 앱 비밀번호를 어디에도 저장하지 않는다. 퍼블릭 레포에서 이게 크다
- 처리 여부를 Gmail 라벨로 표시하므로 이 레포의 무상태 원칙이 유지된다
- `clasp`이 로컬 코드를 Apps Script로 푸시하므로 버전 관리·코드리뷰·변경 이력이 그대로 성립한다 (Node 20+ 필요)

대가는 언어가 섞이는 것이다. 경계는 명확하다 — GAS는 게시까지만, 판정과 리마인드는 Python이다.

### 5.2 리마인드는 GitHub Actions

`finance_reminder`와 동일하다. 판정 로직을 공유하므로 같은 곳에 두는 것이 자연스럽다.

### 5.3 Slack 인증

**Incoming Webhook이 아니라 기존 Slack 앱의 봇 토큰으로 `chat.postMessage`를 호출한다.**

Webhook이 더 간단하지만 게시자가 별개 정체성이 되어, `mail_reminder`가 "이 봇이 올린 글"을 식별하기 어려워진다. 같은 앱을 쓰면 `bot_id`가 고정되어 판정이 명확해지고, 앱이 하나로 유지되어 기수 교체 시 토큰을 하나만 재발급하면 된다.

GAS에서는 `UrlFetchApp`으로 Slack API를 직접 호출하고, 토큰은 Apps Script의 Script Properties에 둔다.

## 6. 선행 리팩터링 — `rules.py` 작성자 조건

**현재 `rules.py`는 이 자동화에 그대로 쓸 수 없다.**

`_is_human_top_level_post()`가 `bot_id`·`app_id`가 있는 메시지를 제외하는데, 메일 게시글은 정확히 봇이 올린 글이다. 그대로 쓰면 대상이 전부 걸러져 **리마인드가 영원히 0건**이 된다. 조용히 실패하는 최악의 형태다.

작성자 조건을 파라미터화한다.

```python
@dataclass(frozen=True)
class Rules:
    ...
    posted_by: str | None = None   # None이면 사람이 쓴 글, 아니면 해당 bot_id
```

동시에 판정 로직을 `automations/finance_reminder/rules.py`에서 `shared/pending.py`로 옮긴다. 두 자동화가 같은 판정을 쓰는 것이 확인된 시점이므로, 이제는 공유 부품으로 올리는 것이 맞다. 각 자동화의 `rules.py`에는 그 자동화 고유의 설정만 남는다.

`finance_reminder`의 기존 테스트는 전부 유지한다. 회귀가 나면 리팩터링이 잘못된 것이다.

## 7. 설정

### mail_ingest (Apps Script Script Properties)

| 이름 | 설명 |
|---|---|
| `SLACK_BOT_TOKEN` | 기존 Slack 앱과 동일한 봇 토큰 |
| `INBOX_CHANNEL_ID` | `#inbox` 채널 ID |
| `GMAIL_QUERY` | 대상 메일 검색어. 자동 반송 제외 규칙을 여기에 둔다 |
| `POSTED_LABEL` | 게시 완료 라벨명. 기본 `slack-posted` |
| `MAX_BODY_CHARS` | 본문 최대 길이. 기본 `3000` |

### mail_reminder (GitHub Variables / Secrets)

| 이름 | 설명 |
|---|---|
| `SLACK_BOT_TOKEN` | Secret. 위와 동일한 토큰 |
| `INBOX_CHANNEL_ID` | `#inbox` 채널 ID |
| `MAIL_BOT_ID` | 메일을 올리는 봇의 `bot_id` |
| `REMIND_AFTER_HOURS` | 기본 `24` |

## 8. 에러 처리

`finance_reminder`와 같은 원칙 — 조용한 실패 금지.

수집 쪽에서 특히 중요한 것:

| 상황 | 처리 |
|---|---|
| Slack 게시 실패 | **라벨을 붙이지 않는다.** 다음 실행에서 다시 시도된다 |
| 게시 성공, 라벨 부착 실패 | 다음 실행에서 중복 게시된다. 중복이 누락보다 낫다 |
| 본문 3,000자 초과 | 자르고 안내를 덧붙인다. 오류가 아니다 |
| Gmail 조회 실패 | 실행 실패. Apps Script가 소유 계정에 오류 메일을 보낸다 |

게시 순서는 **Slack 게시 → 라벨 부착**이다. 순서를 뒤집으면 게시 실패한 메일이 처리된 것으로 표시되어 영구히 사라진다.

## 9. 테스트

GAS 쪽은 Gmail·Slack에 직접 붙으므로 단위 테스트가 어렵다. 순수 함수만 분리해 테스트한다.

- 본문 정리 (인용문 제거, 3,000자 절단)
- 게시 포맷 렌더링
- Gmail 검색어 생성

Python 쪽(`mail_reminder`)은 `finance_reminder`와 같은 방식으로 전부 테스트한다. 특히 `posted_by` 조건은 **봇 글이 대상이 되고 사람 글이 제외되는** 방향을 반드시 검증한다. 이 방향이 뒤집히면 리마인드가 조용히 0건이 된다.

## 10. 인수인계

### ⚠️ Apps Script를 개인 구글 계정에 만들지 말 것

**이 스펙에서 가장 중요한 항목이다.**

Apps Script는 만든 사람의 구글 계정에 귀속된다. 개인 계정에 만들면 그 사람이 졸업하는 순간 스크립트가 멈추고, **아무도 손댈 수 없다.** 코드가 레포에 있어도 실행 중인 인스턴스에 접근할 수 없다.

반드시 **공용 계정 소유**로 만든다. RUNBOOK에 명시한다.

### 그 밖에

- `clasp` 사용법과 배포 절차를 RUNBOOK에 적는다
- Gmail 라벨(`slack-posted`)을 사람이 지우면 그 메일이 다시 게시된다는 점을 적는다
- 트리거는 Apps Script 콘솔에서 확인·재설정하는 방법을 적는다

## 11. 미해결 사항

1. **Apps Script를 둘 공용 구글 계정.** 어느 계정인지, 접근 권한을 누가 갖는지
2. **`#inbox` 채널 생성 및 기존 Slack Email 앱 포워딩 중단 시점.** 둘이 동시에 돌면 메일이 두 번 올라온다
3. **자동 반송 메일의 실제 패턴.** 발신자 주소나 제목으로 거를 수 있는지 표본 확인 필요
4. **공용 계정이 Google Workspace인지 일반 Gmail인지.** Apps Script 정책과 할당량이 다르다
5. **하루 20통이 `#inbox` 채널에서 실제로 감당되는지.** 2주 운영 후 재평가한다

## 12. 다음 단계
