# 회계 송금 리마인더 설계

- 작성일: 2026-08-13
- 상태: 설계 확정 대기
- 대상 자동화: `automations/finance_reminder`

## 1. 배경

회계 채널에서는 운영진이 지출 정산 요청을 올리고, 회계 담당자가 송금을 마친 뒤 원문에 ✅ 리액션을 달아 완료를 표시한다. 이 관행은 봇 도입 이전부터 조직에 정착해 있었다.

문제는 체크가 끝내 달리지 않는 글이 매 기수 상당수 남는다는 것이다. 회계 담당자가 요청을 놓치면 아무도 알아채지 못하고, 요청자는 자기 글이 잊혔다는 사실조차 모른다.

이 자동화의 목적은 **누락 방지** 하나다. 요청자에게 진행 상황을 알리는 투명성 확보나, 미처리 현황 통계는 목적이 아니다.

## 2. 데이터 근거

설계에 앞서 워크스페이스 export(2025-03 ~ 2026-08)를 분석해 가정을 검증했다. 개인정보 보호를 위해 집계값만 기록한다.

| 항목 | 값 |
|---|---|
| 회계 채널 최상위 글 | 208건 |
| 그중 파일(영수증) 첨부 | 122건 (59%) |
| 사용된 리액션 이모지 종류 | 15종 |
| `:white_check_mark:` 사용 | 141회 |
| 2위 이모지 사용 | 4회 |
| 최상위 글 중 리액션 있음 | 63% |
| 직전 기수 미체크 최상위 글 | 29건 |

검증된 사실:

1. **✅ 관행은 이미 확립되어 있다.** 압도적 1위(141회 대 4회)이며, 회계 채널 밖의 공지글에서도 "확인함" 표시로 쓰인다. 봇이 새 규칙을 강요하는 것이 아니라 기존 신호를 읽는다.
2. **미체크 글은 실재하며 규모가 유의미하다.** 직전 기수 기준 29건.
3. **미체크 1위 작성자는 회계 담당자 본인이었다.** 남의 요청을 놓친 것이 아니라 본인이 올린 지출 기록을 마감하지 않은 경우가 가장 많다. 리마인드 대상을 회계 담당자로 삼는 설계는 이 경우에도 유효하다.
4. **워크스페이스에 봇/앱 메시지가 0건이다.** 이것이 첫 Slack 앱 설치이므로, 관리자 승인 절차가 필요한지 구현 전에 확인해야 한다.

### 2.1 기각된 대안: 정산글 자동 판별 필터

"파일 첨부 또는 금액 표기가 있는 글만 대상"이라는 필터를 실데이터로 검증했다.

| 조건 | 표본 | ✅ 비율 |
|---|---|---|
| 파일 첨부 있음 | 58 | 72% |
| 파일도 금액도 없음 | 11 | 9% |

필터는 미체크 29건을 19건으로 줄여 노이즈를 34% 제거한다. 그러나 잘려나가는 10건에 **실제 정산 요청 4건이 포함**되며, 그중에는 금액과 영수증 없이 다급하게 쓴 긴급 요청이 있었다. 급한 요청일수록 형식을 갖추지 않으므로 필터에 먼저 걸린다.

**누락 방지가 목적인 시스템에서 필터가 누락을 만드는 것은 자기모순이다.** 따라서 필터를 두지 않는다. 대신 사람이 ❌ 리액션으로 즉시 제외할 수 있게 한다. 소음은 클릭 한 번으로 영구히 사라지지만, 누락은 되돌릴 방법이 없다.

노이즈 규모는 직전 기수 기준 월 1~2건으로 감당 가능한 수준이다.

## 3. 범위

### 포함
- 회계 채널의 미체크 정산 요청을 매일 요약해 회계 담당자에게 DM
- 위 자동화를 담을 모노레포 골격과 공통 모듈
- 인수인계용 문서 세트

### 제외 (별도 스펙에서 다룸)
- **메일 수집 자동화(`mail_ingest`)** — 메일을 슬랙 채널에 읽기 좋게 게시하는 자동화. Slack 기본 Email 앱은 본문을 첨부 객체로 렌더링해 내용이 보이지 않는데, 이는 설정으로 해결되지 않는 그 앱의 설계다. 리마인드 로직은 이 스펙의 `rules.py`를 채널만 바꿔 재사용하지만, 메일함 접근·본문 렌더링·중복 방지는 별도 설계 영역이다. 사전 조사 결과는 §11.1에 기록한다.
- **공지 확인 리마인더** — 공지에 ✅를 달지 않은 운영진에게 DM. 로직이 거의 동일해 재사용 가치가 높으나 이번 범위 밖.
- 요청자에게 보내는 진행 상황 알림, 미처리 통계·대시보드

## 4. 동작 명세

### 4.1 스케줄

매일 00:00 UTC (09:00 KST)에 1회 실행한다. 요일 구분은 없다. 일과 시작 시각에 맞춰 매일 같은 시간에 도착하는 것을 의도했다.

KST는 서머타임이 없어 UTC 오프셋이 연중 고정이므로 시각이 계절에 따라 밀리지 않는다.

**알려진 지연**: 00:00 UTC는 전 세계 cron이 가장 몰리는 시각이라 GitHub Actions 실행이 십수 분 늦어질 수 있다. 하루 한 번 요약이므로 실용상 문제가 없으나, 도착 시각이 들쭉날쭉해 거슬린다면 `50 23 * * *`(08:50 KST)로 옮긴다. 한산한 시각이라 9시 전에 안정적으로 돈다.

하루 1회 실행이므로 **글이 올라온 뒤 첫 리마인드까지 최대 72시간**(48시간 경과 조건 + 다음 실행까지 최대 24시간)이 걸린다. 의도된 동작이다. 더 빨리 알리려면 실행 주기를 늘리는 것이 아니라 `REMIND_AFTER_HOURS`를 줄인다.

### 4.2 대상 판정

지정 채널의 메시지를 조회 구간 `기수 시작일 00:00 KST 이상, 현재시각 − REMIND_AFTER_HOURS 이하`로 가져온 뒤, 아래를 **모두** 만족하는 메시지를 미처리로 판정한다. 양 끝은 경계값을 포함한다(기수 시작일 당일 글은 대상, 정확히 48시간 경과한 글도 대상).

- 최상위 메시지 (스레드 답글 제외: `thread_ts`가 없거나 `ts`와 같음)
- `subtype`이 없는 사람이 쓴 메시지 (입퇴장 알림 등 제외)
- 봇/앱이 쓴 메시지가 아님 (`bot_id`, `app_id` 없음)
- 완료 이모지(`white_check_mark`) 리액션이 **없음**
- 제외 이모지(`x`) 리액션이 **없음**

리액션 판정은 리액션을 누른 사람이 누구인지 따지지 않는다. 회계 담당자 본인이 올린 글을 본인이 체크하는 경우가 실제로 가장 많기 때문이다.

### 4.3 알림

미처리가 **0건이면 아무것도 보내지 않는다.**

1건 이상이면 회계 담당자 그룹의 각 멤버에게 **개별 DM**을 한 통씩 보낸다. 경과일 내림차순(오래된 것 먼저)으로 정렬한다.

```
💸 아직 송금 안 된 정산 요청 3건입니다.

1. <@U…> — 5일 경과 · <원문 링크|원문 보기>
2. <@U…> — 3일 경과 · <원문 링크|원문 보기>
3. <@U…> — 2일 경과 · <원문 링크|원문 보기>

송금하셨으면 원문에 :white_check_mark: 를 달아주세요.
정산 대상이 아닌 글은 :x: 로 빼면 다음부터 안 뜹니다.
```

작성자는 `<@UXXXX>` 멘션 포맷으로 넣는다. Slack이 이름으로 렌더링해주므로 `users:read` 스코프가 불필요해진다. 권한은 적을수록 좋다.

메시지 본문 미리보기는 넣지 않는다. 회계 채널에는 계좌번호·금액 등이 포함되며, DM에 본문을 복제하면 민감 정보가 한 군데 더 생긴다. 원문 링크로 충분하다.

목록이 20건을 넘으면 상위 20건만 싣고 "외 N건"으로 표기한다. 초기 도입이나 장기 방치 시 DM이 감당 못 할 길이가 되는 것을 막는다.

## 5. 아키텍처

### 5.1 실행 환경

GitHub Actions cron으로 하루 한 번 Python 스크립트를 실행한다. 상시 서버를 두지 않는다.

판정 기준이 "48시간 경과"이므로 실시간 이벤트 수신이 아무런 이득을 주지 않는 반면, 서버는 계속 관리할 사람을 요구해 인수인계 리스크가 된다. 자동화가 늘어날 때도 Actions는 워크플로가 독립이라 격리가 공짜다.

### 5.2 상태 비저장

**이 자동화는 영속 상태를 갖지 않는다.** 매 실행마다 채널 히스토리에서 미처리 목록을 새로 계산한다. "이 글에 이미 알림을 보냈는가"를 기억할 필요가 없다.

매일 요약 방식을 택했기 때문에 얻은 성질이다. 건별 1회 알림이었다면 발송 이력 저장소가 필수였을 것이다. 결과적으로 DB·파일·캐시가 전부 사라지고, 실행이 실패해도 다음 날 자동으로 정상 복구된다.

### 5.3 파일 구조

```
snusv_ax/
├─ README.md                       자동화 목록 인덱스
├─ RUNBOOK.md                      운영·인수인계 가이드
├─ CHANGELOG.md
├─ .env.example
├─ pyproject.toml
├─ docs/
│  ├─ adr/                         설계 결정 기록
│  └─ superpowers/specs/           설계 문서
│
├─ shared/
│  ├─ config.py                    환경변수 로딩 및 검증
│  ├─ slack.py                     Slack API 호출 (재시도 포함)
│  └─ dm.py                        User Group 조회 → 멤버별 DM
│
├─ automations/
│  └─ finance_reminder/
│     ├─ README.md
│     ├─ rules.py                  미처리 판정 (순수 함수)
│     ├─ format.py                 DM 메시지 렌더링
│     └─ main.py                   조립 · CLI
│
├─ tests/
│  ├─ test_rules.py
│  ├─ test_format.py
│  └─ fixtures/messages.json
│
└─ .github/workflows/
   ├─ finance-reminder.yml
   ├─ keepalive.yml
   └─ test.yml
```

자동화를 추가할 때는 `automations/` 아래 폴더 하나와 `.github/workflows/` 아래 yml 하나를 더한다. `shared/`는 자동화가 공유한다.

### 5.4 모듈 경계

**`rules.py`는 Slack을 모른다.** 입력은 메시지 딕셔너리 목록·기준 시각·설정이고, 출력은 미처리 항목 목록이다. 네트워크 호출도, Slack SDK import도 없다.

이 경계 덕분에 48시간 경계·리액션 유무·스레드 답글·봇 메시지 같은 까다로운 케이스를 워크스페이스 없이 전부 테스트할 수 있다. 다음 기수가 규칙을 손볼 때 가장 중요한 성질이다.

`shared/`는 두 번째 자동화가 그대로 쓸 것을 전제로 설계한다. 특히 `dm.py`의 "User Group을 조회해 멤버 각자에게 DM"은 회계 봇 고유 로직이 아니므로 `automations/` 밖에 둔다.

## 6. 설정

전부 환경변수로 주입한다. 코드에 상수로 박지 않는다.

| 이름 | 저장 위치 | 설명 |
|---|---|---|
| `SLACK_BOT_TOKEN` | Secrets | 봇 토큰 (`xoxb-`) |
| `FINANCE_CHANNEL_ID` | Variables | 회계 채널 ID |
| `ACCOUNTANT_USERGROUP` | Variables | 회계 담당자 User Group 핸들 |
| `COHORT_START_DATE` | Variables | 기수 시작일 (`YYYY-MM-DD`) |
| `REMIND_AFTER_HOURS` | Variables | 경과 기준. 기본 `48` |
| `DONE_EMOJI` | Variables | 기본 `white_check_mark` |
| `SKIP_EMOJI` | Variables | 기본 `x` |

토큰만 Secrets에 두고 나머지는 Actions Variables에 둔다. 퍼블릭 레포이므로 채널 ID 같은 조직 내부 식별자도 코드에 남기지 않는다.

기수가 바뀌면 `COHORT_START_DATE` 한 줄만 고친다. 담당자가 바뀌면 코드를 건드리지 않고 Slack User Group 멤버만 교체한다.

## 7. Slack 앱 설정

### 7.1 필요 스코프

봇 토큰 스코프 4개만 요청한다.

- `channels:history` — 채널 히스토리 조회 (비공개 채널이면 `groups:history`)
- `usergroups:read` — 회계 담당자 그룹 멤버 조회
- `chat:write` — DM 발송
- `im:write` — DM 채널 열기

봇을 회계 채널에 **초대해야** 히스토리를 읽을 수 있다.

### 7.2 앱을 배포 상태로 만들지 말 것

Slack은 2025년 5월부터 마켓플레이스 외부에 배포된 앱의 `conversations.history`를 **요청당 15건, 분당 1회**로 제한한다. 기존 설치분에 대한 유예는 2026년 3월 3일에 종료되었다. 반면 **워크스페이스 내부용 커스텀 앱은 예외**로, 요청당 1,000건·분당 50회 이상을 유지한다.

이 봇은 내부 앱이므로 한 기수치 히스토리를 요청 한 번에 가져온다. 그러나 앱 설정에서 배포(distribution)를 활성화하는 순간 같은 작업이 수십 분짜리 폴링으로 변한다. 코드는 그대로인데 봇만 느려지므로 원인 추적이 매우 어렵다.

**앱 설정에서 "Distribute App"을 켜지 않는다.** RUNBOOK 최상단에 명시한다.

## 8. 에러 처리

원칙은 **조용한 실패 금지**다. 아무 일도 하지 않고 초록불이 뜨는 것이 이 봇에서 가장 위험한 상태다.

| 상황 | 처리 |
|---|---|
| 필수 환경변수 누락·형식 오류 | 시작 즉시 실패 |
| `COHORT_START_DATE`가 미래이거나 파싱 불가 | 시작 즉시 실패 |
| User Group 조회 결과 멤버 0명 | 실패 처리 |
| 봇이 채널에 없음 (`not_in_channel`) | 즉시 실패. "봇을 채널에 초대하세요" 안내 출력 |
| 채널 ID·User Group 핸들이 존재하지 않음 | 즉시 실패 |
| Slack 429 응답 | `Retry-After` 준수, 최대 3회 재시도 |
| 그 밖의 Slack API 오류 | 최대 3회 재시도 후 실패 |
| 일부 멤버 DM 실패 | 나머지는 계속 발송, 종료 코드는 실패 |
| 미처리 0건 | 정상 성공 (DM 미발송) |

워크플로가 실패하면 GitHub이 레포 관리자에게 메일을 보낸다. 이것이 유일한 장애 감지 경로이므로, 실패를 성공으로 삼키지 않는 것이 중요하다.

## 9. 테스트

### 9.1 단위 테스트

`rules.py`는 픽스처 JSON으로 테스트한다. 최소 케이스:

- 48시간 경계 (47시간 59분은 제외, 48시간 1분은 포함)
- ✅ 있음 → 제외 / 없음 → 포함
- ❌ 있음 → 제외
- ✅와 ❌가 동시에 있음 → 제외
- 스레드 답글 → 제외
- `channel_join` 등 subtype 있는 메시지 → 제외
- 봇 메시지 → 제외
- 기수 시작일 이전 글 → 제외
- 다른 이모지만 달린 글 → 포함
- 텍스트가 비어 있고 파일만 있는 글 → 포함 (실데이터에 존재함)

`format.py`는 0건·1건·20건 초과 케이스를 검증한다.

### 9.2 드라이런

`--dry-run` 플래그를 지원한다. 실제 채널을 조회해 판정까지 수행하되 DM은 보내지 않고 결과를 표준출력에 찍는다.

워크플로에 `workflow_dispatch`를 넣어 수동 실행할 수 있게 한다. **첫 배포 시 반드시 드라이런으로 먼저 검증한다.**

## 10. 운영

### 10.1 60일 비활성 문제

퍼블릭 레포는 60일간 활동이 없으면 스케줄 워크플로가 자동 비활성화된다. 타이머를 리셋하는 것은 **커밋뿐**이며 이슈·PR·릴리스는 인정되지 않는다. 방학 기간에 정확히 해당한다.

RUNBOOK 경고만으로는 부족하다고 판단해 **월 1회 자동 커밋을 수행하는 `keepalive.yml`을 포함**한다.

### 10.2 문서 세트

| 파일 | 역할 |
|---|---|
| `README.md` | 이 레포가 무엇이고 어떤 자동화가 있는지. 신규 인수자의 진입점 |
| `RUNBOOK.md` | 기수 교체 절차, 담당자 교체 절차, 토큰 재발급, 봇이 안 올 때 점검 순서, 위 지뢰 2개 |
| `CHANGELOG.md` | 무엇이 언제 바뀌었는지 |
| `docs/adr/` | 왜 그렇게 정했는지. 판단의 근거와 기각된 대안 |

변경 사유를 커밋 메시지에만 남기지 않는다. 인수인계 시점에 아무도 찾지 못한다.

작성할 ADR:
- 상시 서버 대신 GitHub Actions를 택한 이유
- 건별 알림 대신 매일 요약을 택한 이유 (상태 비저장을 얻음)
- 정산글 자동 판별 필터를 기각한 이유 (§2.1)
- Slack 앱을 내부 전용으로 유지해야 하는 이유 (§7.2)

### 10.3 퍼블릭 레포 주의

- 토큰·채널 ID·User Group 핸들·실명을 커밋하지 않는다
- 슬랙 export 파일을 레포 안이나 근처에 두지 않는다 (`.gitignore`에 `*.zip` 포함)
- 문서에 조직 구성원을 지칭할 때는 실명 대신 역할로 쓴다

## 11. 확정된 운영 조건

2026-08-13 확정.

1. **Slack 앱 설치** — 워크스페이스 관리자 권한을 보유하고 있어 별도 승인 절차가 없다.
2. **회계 담당자 User Group** — 기존에 없었다. **새로 만들어 앞으로 이 방식으로 관리한다.** 기수마다 회계가 바뀌므로 그룹 멤버만 교체하면 코드를 건드리지 않는다.
3. **회계 채널** — 영수증을 올리는 **공개** 채널이다. 따라서 스코프는 `channels:history`이며 `groups:history`는 불필요하다.
4. **레포 위치** — 개인 계정, 퍼블릭. 조직 계정 이전은 나중에 재검토한다.
5. **`COHORT_START_DATE`** — 39기 공식 시작일 **2026-08-06**.

시작일이 최근이라 첫 실행 시 밀린 물량이 거의 없다. 도입 시점으로 유리하다.

### 11.1 다음 스펙(`mail_ingest`)을 위한 사전 조사

이 스펙의 범위는 아니지만, 조사 결과를 남겨 다음 세션에서 반복하지 않도록 한다.

| 방식 | 비용 | 버전 관리 | 상태 저장 |
|---|---|---|---|
| **Google Apps Script** | 무료 | `clasp`으로 git 동기화 | 불필요 (Gmail 라벨) |
| Python + IMAP on Actions | 무료 | 이 레포 그대로 | **필요** |
| Make.com | 무료 1,000 ops/월 | 레포 밖 | 불필요 |
| Zapier | 무료 100 tasks/월 | 레포 밖 | 불필요 |

Zapier는 무료 플랜이 트리거 1 + 액션 1의 2스텝 제한이라 "수신 → 포맷 → 게시"가 성립하지 않는다. 검토 대상에서 제외한다.

**Google Apps Script가 유력하다.** 구글 계정 권한으로 실행되므로 OAuth 토큰이나 앱 비밀번호를 Secrets에 넣을 필요가 없고, 처리 여부를 Gmail 라벨로 표시하면 되므로 이 레포의 무상태 원칙이 유지된다. `clasp`이 로컬 코드를 Apps Script로 푸시하므로 퍼블릭 레포 버전 관리 목표와도 맞는다(Node 20+ 필요).

참고할 MIT 라이선스 선행 구현: `kemsakurai/gas-Gmail2SlackV2`(본문 길이 제한 설정 가능), `teroyks/gmail-to-slack`(라벨 기반).

대가는 언어가 섞이는 것이다(수집 JavaScript, 판정·알림 Python). 경계는 명확하다 — GAS는 게시까지만, 리마인드는 `rules.py`가 담당한다.

**인수인계 급소**: GAS 스크립트를 개인 구글 계정에 만들면 해당 인원이 졸업할 때 봇이 죽고 아무도 손댈 수 없다. 반드시 공용 계정 소유로 만들고 RUNBOOK에 명시한다.
